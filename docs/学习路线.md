## 二、一次「创建预约」的完整链路

以学生在预约看板点击空闲格、填写用途并提交为例：

```text
浏览器
  │  POST /api/bookings
  │  { deviceId, slotId, date, purpose }
  │  Header: Authorization: Bearer xxx.yyy.zzz
  ▼
Vite Dev Server (:5174)  ── 代理 /api ──▶  Spring Boot (:8091)
                                            │
                                            ▼
                                   AuthInterceptor.preHandle
                                   1. 取 Authorization
                                   2. JwtUtil.parse 校验签名 / 过期
                                   3. AuthContext.set(claims)
                                            │
                                            ▼
                                   BookingController.create()
                                   1. 从 AuthContext 拿 userId
                                   2. 调用 service
                                            │
                                            ▼
                                   BookingService.create()  @Transactional
                                   1. 参数校验（设备 / 日期 / 时段非空）
                                   2. 日期窗口：今天 ≤ date ≤ 今天 + 14 天
                                   3. 设备存在且状态为 AVAILABLE
                                   4. 时段存在，且开始时间晚于当前时间
                                   5. Redis 锁：SET lock:booking:{deviceId}_{date}_{slotId} NX EX 5
                                   6. 同一用户同一天同一时段不能重复
                                   7. 组装 active_key = deviceId_date_slotId
                                   8. insert，捕获 DuplicateKeyException
                                   9. 清理统计缓存（事务提交后）
                                  10. 注册 afterCommit：推送 WebSocket 通知
                                  11. 事务结束：Lua 比对 token 释放锁
                                            │
                                            ▼
                                         MySQL
                                   uk_booking_active 唯一索引兜底
                                            │
                                            ▼
                          Result<Booking>（含联表字段）JSON
                                            │
                                            ▼
                     Axios 拦截器：解包 data / 统一报错 / 401 处理
                                            │
                                            ▼
                BookingBoard.vue 关闭弹窗、刷新矩阵、广播角标事件

              同时：教师 / 管理员的 WebSocket 收到 PENDING_CREATED
                    顶栏铃铛 +1，审批中心自动刷新待审批队列
```

关键点：

- 鉴权发生在 **Controller 之前**，业务代码不用重复解析 token
- 所有「能不能约」的判断都在 **Service**，Controller 只做参数搬运
- 并发冲突不是靠「先查后插」，而是靠 **数据库唯一索引**；Redis 锁只是前置削峰
- 缓存清理和 WebSocket 推送都绑定 **事务提交后**，回滚时不会产生脏缓存 / 假通知
- 前端拿到的是解包后的 `data`，错误提示由拦截器统一弹

## 三、后端分层怎么理解

```text
controller  → 接收参数、拿当前用户、调用 service、返回 Result
service     → 业务规则（状态机、时间窗口、冲突校验、事务边界）
mapper      → SQL（MyBatis 注解，动态条件用 <script>）
model       → 数据库实体
common      → 跨层基础设施（Result、异常、JWT、上下文、分页）
config      → 装配（拦截器、BCrypt、演示数据、定时任务）
```

判断标准：

- **Controller 不写业务判断**：比如「不能审批自己的预约」属于 Service
- **Service 不碰 HTTP**：不出现 `HttpServletRequest`，方便测试和复用
- **Mapper 只做数据访问**：不写「如果为空就报错」这类业务逻辑
- **状态流转一定带前置条件**：SQL 里写 `where status = 'PENDING'`，而不是先查再改

## 四、数据库设计

系统共 5 张表：

```text
sys_user            用户（username 唯一，password 存 BCrypt 哈希）
device_category     设备分类（code、name 唯一）
device              设备（code 唯一，category_id 逻辑外键）
time_slot           预约时段（start_time / end_time / sort_no）
booking             预约（active_key 唯一，用于防重复占位）
```

`booking` 的核心字段：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 预约人 |
| `device_id` | 设备 |
| `slot_id` | 时段 |
| `booking_date` | 预约日期（`DATE`） |
| `status` | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` / `COMPLETED` / `VIOLATED` |
| `active_key` | `deviceId_date_slotId`，仅有效预约持有 |
| `approver_id` / `approve_remark` / `approved_at` | 审批信息 |
| `checkin_at` | 签到时间 |
| `created_at` | 创建时间 |

设计取舍：

- **不建物理外键**：互联网项目常用「逻辑外键 + 索引」，便于迁移和分库分表；分类 / 设备是否存在由 Service 校验
- **状态用字符串**：可读性好，排查问题直观；合法性由 Service 和状态机保证
- **唯一索引而不是先查后插**：并发下先查后插有竞态，唯一索引由数据库保证原子性

```sql
UNIQUE KEY uk_booking_active (active_key)
```

释放占位：

```sql
UPDATE booking
SET status = 'CANCELLED', active_key = NULL
WHERE id = ? AND user_id = ? AND status IN ('PENDING', 'APPROVED');
```

为什么置 `NULL` 就能释放？因为 MySQL 唯一索引允许多个 `NULL`，历史记录不会互相冲突。

## 五、预约状态机

```text
                    ┌────────────── 用户取消（开始前） ─────────────┐
                    ▼                                              │
 提交预约 ──▶ PENDING ──教师通过──▶ APPROVED ──签到──▶（时段结束）COMPLETED
                │                     │
                │                     └── 未签到，时段结束 ──▶ VIOLATED
                ├──教师驳回──▶ REJECTED
                └──时段开始仍未审批──▶ CANCELLED（系统自动）
```

每条规则在代码里的位置：

| 规则 | 实现位置 | 说明 |
| --- | --- | --- |
| 可预约日期 | `BookingService.create` | 今天起 14 天内 |
| 设备可用 | `BookingService.create` | 只允许 `AVAILABLE` |
| 时段未开始 | `BookingService.create` | `start > now` |
| 用户同时段唯一 | `BookingService.create` | `countUserSlot > 0` 直接拒绝 |
| 设备同时段唯一 | 数据库唯一索引 | 捕获 `DuplicateKeyException` |
| 取消 | `BookingService.cancel` | 本人 + 有效状态 + 未开始 |
| 审批 | `BookingService.approve` | 只能 `PENDING`、不能审批自己、未开始 |
| 签到 | `BookingService.checkin` | `APPROVED` + 未签到 + 开始前 30 分钟至结束 |
| 自动流转 | `BookingService.refreshStatuses` | 完成 / 违约 / 超时取消 |

**状态机最重要的思想：每个动作都先判断「当前状态是否允许」，再用带条件的 SQL 更新。**
这样即使两个请求同时到达，也只有一个能成功。

```java
int rows = bookingMapper.approve(id, staffId, remark);
if (rows == 0) {
    throw BizException.badRequest("审批失败，请刷新后重试");
}
```

对应 SQL：

```sql
UPDATE booking
SET status = 'APPROVED', approver_id = ?, approve_remark = ?, approved_at = NOW()
WHERE id = ? AND status = 'PENDING';
```

## 六、并发控制：唯一索引到底解决了什么

假设两个学生同时预约「D002 图形工作站，10-30，14:00-16:00」。

### 错误做法：先查后插

```text
请求 A: select ... 没有冲突
请求 B: select ... 没有冲突
请求 A: insert 成功
请求 B: insert 成功   ← 重复占位
```

「查」和「插」之间有时间窗口，两个请求都能通过检查。

### 正确做法：数据库唯一索引

```text
请求 A: insert active_key = 2_2026-10-30_3  成功
请求 B: insert active_key = 2_2026-10-30_3  唯一键冲突
```

Service 捕获异常，转成用户能看懂的提示：

```java
try {
    bookingMapper.insert(booking);
} catch (DuplicateKeyException e) {
    throw BizException.badRequest("该设备的这个时段已被预约，请选择其他时段");
}
```

要点：

- **先查是为了给出友好提示，唯一索引才是最终保障**
- 唯一索引的原子性由 InnoDB 保证，应用层不需要加锁
- `active_key` 只在有效状态持有，取消 / 驳回 / 完成 / 违约后置空
- 如果将来要做「并发量很大」的抢约，可以再加 Redis 分布式锁做前置削峰，但数据库约束仍然要保留（第三阶段已实现，见后文第十二章）

### `@Transactional` 在这里的作用

- 创建预约：插入 + 回查详情，保持一致性
- 审批：查状态 + 更新，异常时整体回滚
- 状态刷新：同一批预约的多次更新要么都生效要么都回滚

注意：**`@Transactional` 默认只对 `RuntimeException` 回滚**，项目里的 `BizException` 继承自 `RuntimeException`，所以能正常回滚。

## 七、定时任务与「懒刷新」

预约状态不能只靠用户操作触发，否则「时段结束后自动完成 / 违约」永远不会发生。

```java
@Scheduled(fixedDelay = 60_000, initialDelay = 15_000)
public void refresh() {
    try {
        bookingStatusService.refreshStatuses();
    } catch (Exception e) {
        log.warn("预约状态刷新失败：{}", e.getMessage());
    }
}
```

三个细节：

1. **`fixedDelay` 而不是 `fixedRate`**：上一次执行完再等 60 秒，避免任务堆积
2. **异常必须吞掉**：定时任务抛异常会导致后续调度停止（取决于线程池配置），这里记录日志继续跑
3. **查询前也刷新一次**：`listByDate` / `mine` / `pageAll` 都会调用 `refreshStatuses()`，保证用户打开页面看到的是最新状态，不用等下一分钟

状态刷新逻辑：

```java
// 已通过且时段已结束
if (checkinAt != null) → COMPLETED
else                   → VIOLATED

// 待审批但时段已开始
→ CANCELLED
```

为什么可以重复执行？因为每次更新都带 `where status = 'APPROVED'` 之类的条件，已经是 `COMPLETED` 的记录不会再次被处理，**天然幂等**。

## 八、统计 SQL 与趋势补零

统计模块的原则：**能在数据库聚合的，不要拉到内存**。

```sql
-- 状态分布
SELECT status AS name, COUNT(*) AS value
FROM booking
GROUP BY status;

-- 设备热度
SELECT d.name AS name, COUNT(*) AS value
FROM booking b JOIN device d ON d.id = b.device_id
GROUP BY d.id, d.name
ORDER BY value DESC
LIMIT 5;
```

趋势查询只返回「有数据的日期」，Service 在 Java 侧补齐缺失日期：

```java
Map<LocalDate, Long> counted = ...;  // SQL 结果
for (int i = days - 1; i >= 0; i--) {
    LocalDate day = today.minusDays(i);
    result.add(Map.of(
        "date", day.toString(),
        "label", day.format(DateTimeFormatter.ofPattern("MM-dd")),
        "value", counted.getOrDefault(day, 0L)
    ));
}
```

为什么要补零？

- 折线图如果缺少日期，X 轴会「跳变」，看起来像数据错误
- 补零后趋势连续，业务上也能看出「某天真的没人预约」

注意 JDBC 返回的可能是 `java.sql.Date`，用 `toLocalDate()` 转换，避免 `ClassCastException`。

> 第三阶段给这些统计方法加了 `@Cacheable`，并用 `StatsCacheEvictor` 在预约变更后清理缓存。缓存不能替代聚合 SQL，只是减少重复计算。

## 九、前端：预约矩阵与深色科技风

### 9.1 预约矩阵

数据结构是「设备 × 时段」，用 CSS Grid 渲染：

```html
<div class="matrix" :style="{ gridTemplateColumns: `196px repeat(${slots.length}, minmax(132px, 1fr))` }">
```

为什么用内联 `gridTemplateColumns`？

- 时段数量是接口返回的，CSS 变量在 `repeat()` 里兼容性差
- 内联样式能直接拿到响应式数据，避免动态生成 `<style>`

单元格状态由前端根据「预约记录 + 当前时间 + 设备状态」计算：

| 状态 | 条件 | 样式 |
| --- | --- | --- |
| 可预约 | 无预约、设备可用、时段未开始 | 青色边框，可点击 |
| 待审批 | 有 `PENDING` | 黄色 |
| 已通过 | 有 `APPROVED` | 蓝色 |
| 已完成 | 有 `COMPLETED` | 绿色 |
| 违约 | 有 `VIOLATED` | 红色 |
| 不可用 | 设备维修 / 停用 | 灰色 |
| 已过期 | 时段已开始且无预约 | 暗色，不可点击 |

日期边界：今天起 14 天，`canPrev` / `canNext` 控制按钮禁用，避免用户翻到无意义的日期。

### 9.2 深色主题

- `document.documentElement.classList.add('dark')` 启用 Element Plus 暗色变量
- `styles/global.css` 定义 CSS 变量：背景、面板、边框、霓虹色
- 登录页 / 仪表盘用纯 CSS 做网格背景、光晕、雷达扫描、扫描线
- 所有页面共用玻璃面板：`background: rgba(...)` + `backdrop-filter: blur(...)` + 细边框

### 9.3 ECharts 按需引入

完整 `echarts` 包很大，项目只用到折线、环形饼图、横向柱状图：

```js
import * as echarts from 'echarts/core'
import { BarChart, LineChart, PieChart } from 'echarts/charts'
import { GridComponent, TooltipComponent, LegendComponent, GraphicComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'

echarts.use([...])
```

构建结果：`echarts` chunk 约 531 KB（gzip 179 KB），比完整包小很多。

注意一个坑：`utils/echarts.js` 默认导出的是命名空间对象，页面里要写：

```js
import echarts from '../utils/echarts'
```

而不是 `import * as echarts`，否则会多包一层，`echarts.graphic` 取不到。

### 9.4 侧边栏角标即时刷新

待审批数量在 `MainLayout` 里轮询（60 秒一次），但用户提交预约 / 审批后不应该等一分钟。

方案：自定义事件。

```js
// 提交预约后
window.dispatchEvent(new Event('lab:pending-changed'))

// MainLayout
window.addEventListener('lab:pending-changed', loadBadge)
```

比引入事件总线或 Pinia 全局状态更轻，组件卸载时记得 `removeEventListener`。

### 9.5 构建分包

```js
manualChunks: {
  vue: ['vue', 'vue-router', 'pinia', 'axios'],
  'element-plus': ['element-plus'],
  'element-icons': ['@element-plus/icons-vue'],
  echarts: ['echarts/core', 'echarts/charts', 'echarts/components', 'echarts/renderers'],
}
```

好处：第三方依赖单独缓存，业务代码更新时用户不用重新下载 900 KB 的 Element Plus。
另外只注册项目实际用到的 20 个图标，图标 chunk 从 170 KB 降到 26 KB。

## 十、调试方法

### 10.1 后端

```powershell
# 健康检查
curl.exe http://127.0.0.1:8091/api/health

# 登录取 token（Windows PowerShell 建议用文件传 JSON）
'{"username":"admin","password":"123456"}' | Set-Content "$env:TEMP\login.json" -Encoding utf8 -NoNewline
curl.exe -s -X POST http://127.0.0.1:8091/api/auth/login `
  -H "Content-Type: application/json" --data-binary "@$env:TEMP\login.json"

# 带 token 请求
curl.exe -s http://127.0.0.1:8091/api/bookings/day `
  -H "Authorization: Bearer <token>"
```

> PowerShell 5.1 里内联 `-d '{"..."}'` 容易被引号解析吃掉，出现 `JSON parse error: Unexpected character`，用临时文件最稳。

### 10.2 前端

- Network 面板看请求头是否带 `Authorization`
- 401：token 过期或没带上
- 403：登录了但角色不够
- 400：业务校验失败，看 `message`
- 看板空白：先看 Console 是否有 ECharts 报错，再看接口是否返回数据

### 10.3 一个完整的接口验证顺序

```text
1. 登录拿 token
2. GET  /api/slots                 确认时段
3. GET  /api/bookings/day          确认某天矩阵
4. POST /api/bookings              创建预约（PENDING）
5. POST /api/bookings             再次提交 → 应提示重复
6. POST /api/bookings/{id}/approve 教师审批 → APPROVED
7. GET  /api/bookings/my?status=APPROVED  确认状态
8. POST /api/bookings/{id}/checkin 签到（需在窗口内）
9. POST /api/bookings/{id}/cancel  取消 → 释放 active_key
10. GET /api/stats/*               确认统计数字变化
```

## 十一、面试可能会问

### 基础

1. **为什么用 JWT？和 Session 有什么区别？**
   无状态、易扩展；代价是无法主动失效，需要黑名单或短有效期 + 刷新 token。

2. **JWT 的 payload 能放密码吗？**
   不能，payload 只是 Base64URL 编码，可被解码。

3. **ThreadLocal 为什么要在 `afterCompletion` 清理？**
   Tomcat 线程池复用线程，不清理会导致用户信息串号、内存泄漏。

4. **前端做了权限校验，后端还要做吗？**
   必须。前端可被绕过，后端才是安全边界。

### 并发与事务

5. **唯一索引和先查后插哪个更可靠？**
   并发下先查后插有竞态；唯一索引由数据库保证原子性，捕获重复键异常即可。

6. **`active_key` 为什么取消后要置空？**
   MySQL 唯一索引对 `NULL` 不生效（允许多个 `NULL`），置空即释放占位。

7. **`@Transactional` 什么情况下会失效？**
   同类内部方法调用、非 `public` 方法、异常被吞掉、异常类型不是 `RuntimeException`（默认）、多数据源未配置事务管理器。

8. **审批接口如何防止重复审批？**
   SQL 带 `where status = 'PENDING'`，更新行数为 0 就提示「已被处理」；这是乐观锁思想。

9. **如果两个人同时审批同一条预约会怎样？**
   只有一个 `UPDATE` 能命中 `PENDING`，另一个返回 0 行并提示刷新，不会产生两次审批记录。

### 状态机与定时任务

10. **为什么需要定时任务？**
    状态变化不只由用户触发：时段结束要自动完成 / 违约，超时未审批要自动取消。

11. **`fixedDelay` 和 `fixedRate` 的区别？**
    `fixedDelay` 是上一次执行完再等，`fixedRate` 是固定频率；任务耗时可能超过间隔时，`fixedRate` 会堆积。

12. **定时任务如何保证幂等？**
    每次更新都带状态条件，已流转的记录不会被再次处理。

13. **签到窗口为什么设在开始前 30 分钟？**
    既要允许学生提前到场，又要防止提前太久「占坑不签」。

### 统计与前端

14. **为什么统计用 SQL 聚合而不是 Java 循环？**
    数据量大时内存和网络开销高；数据库有索引和聚合优化。

15. **趋势图为什么要补零？**
    保证 X 轴连续，避免折线跳变和误判。

16. **ECharts 在 Vue 里要注意什么？**
    容器有宽高、初始化一次、监听 resize、卸载时 `dispose`。

17. **为什么用 `manualChunks` 分包？**
    第三方依赖体积大且不常变，单独分包可利用浏览器缓存，业务代码更新不影响依赖缓存。

18. **自定义事件和 Pinia 怎么选？**
    简单的一次性通知用事件更轻；跨页面共享状态用 Pinia。

### 缓存、锁与实时通信

19. **为什么缓存注解加在 Service 而不是 Controller？**
    Controller 负责 HTTP，缓存属于业务能力；加在 Service 才能被其他 Service 复用，也避免缓存 HTTP 对象。

20. **为什么预约变更后是「删缓存」而不是「更新缓存」？**
    更新缓存需要知道所有受影响的 key（分页参数、统计维度），容易漏；删除后下次读自然回源，逻辑简单且不易不一致。

21. **为什么缓存清理要放在事务提交后？**
    如果事务回滚，缓存已经被清空只是多一次回源；但如果先写缓存再回滚，就会留下脏数据。提交后清理更安全。

22. **Redis 分布式锁为什么必须用 Lua 解锁？**
    要先比较 token 再删除，这两个操作必须原子；否则锁过期后被别人拿到，旧请求可能误删新锁。

23. **有了 Redis 锁，还需要数据库唯一索引吗？**
    需要。锁可能因超时、Redis 故障、网络分区失效；唯一索引是最终正确性保障。

24. **WebSocket 为什么不用 `Authorization` 头？**
    浏览器原生 WebSocket API 不支持自定义请求头，所以用查询参数或 Cookie 传递凭证。

25. **WebSocket 推送为什么放在 `afterCommit`？**
    事务回滚时不能发「预约成功」；提交后推送才能保证消息与数据库状态一致。

26. **多实例部署时 WebSocket 会有什么问题？**
    用户的连接可能落在实例 A，业务请求落在实例 B；需要 Redis Pub/Sub、STOMP Relay 或消息队列做跨实例广播。当前项目是单实例演示。

## 十二、Redis：缓存与分布式锁

### 12.1 为什么缓存，缓存什么

预约系统的读请求远多于写请求：

- 设备分页、分类列表：几乎每次打开页面都查
- 统计接口：多次 `GROUP BY`，重复计算成本高
- 预约矩阵：实时性要求高，**不缓存**

所以只缓存「读多写少、能接受几十秒延迟」的数据，并给不同业务设置不同 TTL：

| 数据 | TTL | 理由 |
| --- | --- | --- |
| 设备分页 | 60 秒 | 设备台账变化不频繁 |
| 分类 | 5 分钟 | 极少变化 |
| 统计总览 | 30 秒 | 看板容忍短暂延迟 |
| 趋势 / 分布 / 热度 | 60 秒 | 图表不需要秒级实时 |

### 12.2 本地缓存与 Redis 如何切换

```java
@Bean
@ConditionalOnProperty(name = "app.redis.enabled", havingValue = "true")
public RedisCacheManager redisCacheManager(RedisConnectionFactory factory) { ... }
```

- 未开启：Spring Boot 按 `spring.cache.type=caffeine` 创建 `CaffeineCacheManager`
- 开启：显式注册 `RedisCacheManager`，Spring Boot 自动退让
- 接口层完全无感，`@Cacheable` / `@CacheEvict` 不变

这就是「面向接口编程」的好处：业务只依赖 `CacheManager` 抽象。

### 12.3 缓存一致性策略

项目采用 **Cache Aside**：

```text
读：先查缓存 → 未命中查库 → 写缓存
写：更新数据库 → 删除缓存（而不是更新缓存）
```

工程细节：

1. **删除缓存放在事务提交后**：`RedisCacheManager.transactionAware()` 会把清理操作延迟到提交后
2. **只删受影响的缓存**：设备变更删设备分页 + 分类 + 相关统计；预约变更只删统计
3. **统计缓存统一清理**：`StatsCacheEvictor` 遍历 `CacheNames.STATS_ALL`
4. **缓存异常不影响业务**：`CacheErrorHandler` 只记录限流日志，方法继续查库

### 12.4 三大缓存问题

| 问题 | 现象 | 本项目做法 | 进一步优化 |
| --- | --- | --- | --- |
| 缓存穿透 | 查不存在的数据，每次都打库 | `disableCachingNullValues` + 业务校验（设备不存在直接 400） | 空值短缓存、布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间大量请求打库 | 总览使用 `sync = true`，同 key 只放一个线程回源 | 逻辑过期 + 互斥重建 |
| 缓存雪崩 | 大量 key 同时过期 | TTL 按业务分层（30s / 60s / 5min） | TTL 加随机抖动、Redis 高可用 |

> 注意：`sync = true` 只保证单实例内合并回源；多实例仍需分布式锁或逻辑过期。

### 12.5 抢约分布式锁

以「D002 图形工作站，10-30，14:00-16:00」为例：

```text
key   = lock:booking:2_2026-10-30_3
token = UUID
SET key token NX EX 5
```

为什么这样设计：

- `NX`：只有 key 不存在才设置，天然互斥
- `EX 5`：进程崩溃后锁自动释放，避免死锁
- `token`：标识锁的持有者，解锁时必须比对
- Lua：`GET` + `DEL` 必须原子，防止误删别人的锁

释放时机非常关键：

```java
try {
    // 业务 + insert
} finally {
    redisLock.unlockAfterCompletion(lockKey, lockToken);
}
```

`unlockAfterCompletion` 会把释放动作注册到 `TransactionSynchronization.afterCompletion`：

- 如果事务还没提交就释放锁，下一个请求可能在当前事务提交前拿到锁
- 两个事务都通过「查重」，最后仍然会在唯一索引上撞车
- 放到提交 / 回滚之后释放，才真正串行化「检查 + 写入 + 提交」

锁的定位：

```text
Redis 锁：减少并发冲突、保护数据库、给用户友好提示
唯一索引：最终正确性保障，绝不超卖
```

### 12.6 序列化踩坑：`LinkedHashMap cannot be cast to PageResult`

第一版使用：

```java
new GenericJackson2JsonRedisSerializer(objectMapper)
```

结果第二次请求直接 500：

```text
class java.util.LinkedHashMap cannot be cast to class com.lab.common.PageResult
```

原因：

- 没有开启 `defaultTyping`，JSON 里没有类型信息
- 反序列化只能得到 `LinkedHashMap`
- Spring 代理返回时按方法签名做强转，触发 `ClassCastException`

修复：

```java
GenericJackson2JsonRedisSerializer.builder()
        .objectMapper(mapper)
        .defaultTyping(true)
        .registerNullValueSerializer(true)
        .build();
```

同时注册 `JavaTimeModule`，否则 `LocalDate` / `LocalDateTime` 也无法序列化。

这个坑很值得讲：**缓存不是把对象丢进去就完事，序列化方式决定了能不能还原成原类型。**

### 12.7 验证方式


## 十三、WebSocket：实时通知

### 13.1 为什么不用轮询

| 方案 | 延迟 | 服务器压力 | 实现复杂度 |
| --- | --- | --- | --- |
| 3 秒轮询 | 0~3 秒 | 大量无效请求 | 低 |
| 长轮询 | 较低 | 连接占用多 | 中 |
| WebSocket | 毫秒级 | 连接常驻，消息按需推 | 中 |

预约审批是「低频但要及时」的事件，轮询会浪费大量请求；WebSocket 更合适。

### 13.2 握手鉴权

浏览器 API：

```js
new WebSocket(`ws://host/ws/notifications?token=${token}`)
```

不能写：

```js
new WebSocket(url, { headers: { Authorization: ... } }) // 浏览器不支持
```

服务端在握手阶段解析 token：

```java
JwtUtil.Claims claims = jwtUtil.parse(token);
attributes.put("uid", claims.uid());
attributes.put("role", claims.role());
```

校验失败返回 HTTP 401，连接不会建立。

### 13.3 会话管理

```java
Map<Long, Set<WebSocketSession>> userSessions;
Map<String, String> sessionRoles;
```

- key 是用户 id，value 是会话集合：支持同一用户多标签页
- `ConcurrentHashMap` + `newKeySet()`：并发安全
- 连接关闭时移除会话，集合为空则移除用户
- 发送时对 `session` 加锁：`WebSocketSession` 不是线程安全的

### 13.4 推送时机

```java
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    registerSynchronization(new TransactionSynchronization() {
        public void afterCommit() { handler.sendToUser(...); }
    });
} else {
    handler.sendToUser(...);
}
```

为什么要 `afterCommit`：

- 事务回滚后不能发「预约成功」
- 推送是 I/O，不应该占用数据库事务时间
- 推送失败只记录日志，不能影响主业务

### 13.5 前端生命周期

```text
登录成功 → MainLayout onMounted → connectSocket(token)
                │
                ├─ onopen：状态 REALTIME，启动 25s 心跳
                ├─ onmessage：JSON 解析 → 订阅者分发
                ├─ onclose：状态 OFFLINE，指数退避重连
                └─ 退出登录 / 卸载：closeSocket()，禁止重连
```

关键点：

- `manuallyClosed` 区分「主动关闭」和「意外断线」
- 重连延迟 `1s → 2s → 4s → ... → 30s`，避免服务端刚重启就被打满
- 先订阅再连接，避免漏掉 `CONNECTED` 之后的第一条业务消息
- `onBeforeUnmount` 解绑订阅并关闭连接，防止重复连接

### 13.6 消息分流

前端收到消息后分两类处理：

```js
if (type === 'PENDING_CHANGED' || type === 'PENDING_CREATED') {
  loadBadge()
  window.dispatchEvent(new Event('lab:pending-changed'))
}
if (type.startsWith('BOOKING_')) {
  window.dispatchEvent(new Event('lab:booking-changed'))
}
```

- `PENDING_CHANGED`：静默刷新，不打扰用户
- `BOOKING_*`：进入消息中心 + Element Plus 通知 + 页面数据刷新
- 页面用 `lab:booking-changed` 监听，400~500ms 防抖后重新拉数据

### 13.7 常见坑

1. **代理没开 WebSocket**：Vite 需要 `ws: true`，Nginx 需要 `Upgrade` / `Connection`
2. **Nginx 超时**：默认 60 秒无数据会断开，需调大 `proxy_read_timeout`
3. **token 泄漏**：查询参数会进访问日志，生产环境改用 HttpOnly Cookie / 一次性 ticket
4. **多实例**：连接和请求可能不在同一台机器，需要 Redis Pub/Sub 或 STOMP Relay
5. **离线消息**：当前只推在线用户，后续需要站内信落库 + 未读数

## 十四、Docker Compose：一键部署

### 14.1 多阶段构建

后端：

```dockerfile
FROM maven:3.9.9-eclipse-temurin-17 AS build
COPY pom.xml .
RUN mvn -q -B -DskipTests dependency:go-offline
COPY src ./src
RUN mvn -q -B -DskipTests package

FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/*.jar app.jar
```

好处：

- 运行镜像不包含 Maven、源码、构建缓存
- `pom.xml` 单独一层：依赖不变时复用缓存，构建更快
- 前端同理：Node 只负责构建，最终镜像只有 Nginx + 静态文件

### 14.2 Compose 编排

```yaml
services:
  mysql: ...
  redis: ...
  backend:
    depends_on:
      mysql: { condition: service_healthy }
      redis: { condition: service_healthy }
  frontend:
    depends_on:
      backend: { condition: service_healthy }
```

健康检查比 `depends_on` 的「启动顺序」更可靠：容器启动了不代表服务可用。

### 14.3 Nginx 的三个职责

1. 托管前端静态文件 + SPA 路由回退
2. 反向代理 `/api` 到后端
3. 反向代理 `/ws` 并转发 WebSocket Upgrade

```nginx
location /ws/ {
    proxy_pass http://backend:8091;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
}
```

### 14.4 镜像与数据

- MySQL 数据卷：`mysql-data`
- Redis 数据卷：`redis-data`（只存缓存 / 锁，丢失可重建）
- `.env` 注入密码与密钥，不进入镜像
- `.dockerignore` 排除 `target/`、`node_modules/`、`.git/`、本地配置文件
