## 二、一次「创建预约」的完整链路

以学生在预约看板点击空闲格、填写用途并提交为例：

```text
浏览器
  │  POST /api/bookings
  │  { deviceId, slotId, date, purpose }
  │  Header: Authorization: Bearer xxx.yyy.zzz
  ▼
Vite Dev Server (:5174)  ── 代理 /api ──▶  Spring Boot (:8091)
                                            │
                                            ▼
                                   AuthInterceptor.preHandle
                                   1. 取 Authorization
                                   2. JwtUtil.parse 校验签名 / 过期
                                   3. AuthContext.set(claims)
                                            │
                                            ▼
                                   BookingController.create()
                                   1. 从 AuthContext 拿 userId
                                   2. 调用 service
                                            │
                                            ▼
                                   BookingService.create()  @Transactional
                                   1. 参数校验（设备 / 日期 / 时段非空）
                                   2. 日期窗口：今天 ≤ date ≤ 今天 + 14 天
                                   3. 设备存在且状态为 AVAILABLE
                                   4. 时段存在，且开始时间晚于当前时间
                                   5. 同一用户同一天同一时段不能重复
                                   6. 组装 active_key = deviceId_date_slotId
                                   7. insert，捕获 DuplicateKeyException
                                            │
                                            ▼
                                         MySQL
                                   uk_booking_active 唯一索引兜底
                                            │
                                            ▼
                          Result<Booking>（含联表字段）JSON
                                            │
                                            ▼
                     Axios 拦截器：解包 data / 统一报错 / 401 处理
                                            │
                                            ▼
                BookingBoard.vue 关闭弹窗、刷新矩阵、广播角标事件
```

关键点：

- 鉴权发生在 **Controller 之前**，业务代码不用重复解析 token
- 所有「能不能约」的判断都在 **Service**，Controller 只做参数搬运
- 并发冲突不是靠「先查后插」，而是靠 **数据库唯一索引**
- 前端拿到的是解包后的 `data`，错误提示由拦截器统一弹

## 三、后端分层怎么理解

```text
controller  → 接收参数、拿当前用户、调用 service、返回 Result
service     → 业务规则（状态机、时间窗口、冲突校验、事务边界）
mapper      → SQL（MyBatis 注解，动态条件用 <script>）
model       → 数据库实体
common      → 跨层基础设施（Result、异常、JWT、上下文、分页）
config      → 装配（拦截器、BCrypt、演示数据、定时任务）
```

判断标准：

- **Controller 不写业务判断**：比如「不能审批自己的预约」属于 Service
- **Service 不碰 HTTP**：不出现 `HttpServletRequest`，方便测试和复用
- **Mapper 只做数据访问**：不写「如果为空就报错」这类业务逻辑
- **状态流转一定带前置条件**：SQL 里写 `where status = 'PENDING'`，而不是先查再改

## 四、数据库设计

第二阶段共 5 张表：

```text
sys_user            用户（username 唯一，password 存 BCrypt 哈希）
device_category     设备分类（code、name 唯一）
device              设备（code 唯一，category_id 逻辑外键）
time_slot           预约时段（start_time / end_time / sort_no）
booking             预约（active_key 唯一，用于防重复占位）
```

`booking` 的核心字段：

| 字段 | 说明 |
| --- | --- |
| `user_id` | 预约人 |
| `device_id` | 设备 |
| `slot_id` | 时段 |
| `booking_date` | 预约日期（`DATE`） |
| `status` | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` / `COMPLETED` / `VIOLATED` |
| `active_key` | `deviceId_date_slotId`，仅有效预约持有 |
| `approver_id` / `approve_remark` / `approved_at` | 审批信息 |
| `checkin_at` | 签到时间 |
| `created_at` | 创建时间 |

设计取舍：

- **不建物理外键**：互联网项目常用「逻辑外键 + 索引」，便于迁移和分库分表；分类 / 设备是否存在由 Service 校验
- **状态用字符串**：可读性好，排查问题直观；合法性由 Service 和状态机保证
- **唯一索引而不是先查后插**：并发下先查后插有竞态，唯一索引由数据库保证原子性

```sql
UNIQUE KEY uk_booking_active (active_key)
```

释放占位：

```sql
UPDATE booking
SET status = 'CANCELLED', active_key = NULL
WHERE id = ? AND user_id = ? AND status IN ('PENDING', 'APPROVED');
```

为什么置 `NULL` 就能释放？因为 MySQL 唯一索引允许多个 `NULL`，历史记录不会互相冲突。

## 五、预约状态机

```text
                    ┌────────────── 用户取消（开始前） ─────────────┐
                    ▼                                              │
 提交预约 ──▶ PENDING ──教师通过──▶ APPROVED ──签到──▶（时段结束）COMPLETED
                │                     │
                │                     └── 未签到，时段结束 ──▶ VIOLATED
                ├──教师驳回──▶ REJECTED
                └──时段开始仍未审批──▶ CANCELLED（系统自动）
```

每条规则在代码里的位置：

| 规则 | 实现位置 | 说明 |
| --- | --- | --- |
| 可预约日期 | `BookingService.create` | 今天起 14 天内 |
| 设备可用 | `BookingService.create` | 只允许 `AVAILABLE` |
| 时段未开始 | `BookingService.create` | `start > now` |
| 用户同时段唯一 | `BookingService.create` | `countUserSlot > 0` 直接拒绝 |
| 设备同时段唯一 | 数据库唯一索引 | 捕获 `DuplicateKeyException` |
| 取消 | `BookingService.cancel` | 本人 + 有效状态 + 未开始 |
| 审批 | `BookingService.approve` | 只能 `PENDING`、不能审批自己、未开始 |
| 签到 | `BookingService.checkin` | `APPROVED` + 未签到 + 开始前 30 分钟至结束 |
| 自动流转 | `BookingService.refreshStatuses` | 完成 / 违约 / 超时取消 |

**状态机最重要的思想：每个动作都先判断「当前状态是否允许」，再用带条件的 SQL 更新。**
这样即使两个请求同时到达，也只有一个能成功。

```java
int rows = bookingMapper.approve(id, staffId, remark);
if (rows == 0) {
    throw BizException.badRequest("审批失败，请刷新后重试");
}
```

对应 SQL：

```sql
UPDATE booking
SET status = 'APPROVED', approver_id = ?, approve_remark = ?, approved_at = NOW()
WHERE id = ? AND status = 'PENDING';
```

## 六、并发控制：唯一索引到底解决了什么

假设两个学生同时预约「D002 图形工作站，10-30，14:00-16:00」。

### 错误做法：先查后插

```text
请求 A: select ... 没有冲突
请求 B: select ... 没有冲突
请求 A: insert 成功
请求 B: insert 成功   ← 重复占位
```

「查」和「插」之间有时间窗口，两个请求都能通过检查。

### 正确做法：数据库唯一索引

```text
请求 A: insert active_key = 2_2026-10-30_3  成功
请求 B: insert active_key = 2_2026-10-30_3  唯一键冲突
```

Service 捕获异常，转成用户能看懂的提示：

```java
try {
    bookingMapper.insert(booking);
} catch (DuplicateKeyException e) {
    throw BizException.badRequest("该设备的这个时段已被预约，请选择其他时段");
}
```

要点：

- **先查是为了给出友好提示，唯一索引才是最终保障**
- 唯一索引的原子性由 InnoDB 保证，应用层不需要加锁
- `active_key` 只在有效状态持有，取消 / 驳回 / 完成 / 违约后置空
- 如果将来要做「并发量很大」的抢约，可以再加 Redis 分布式锁做前置削峰，但数据库约束仍然要保留

### `@Transactional` 在这里的作用

- 创建预约：插入 + 回查详情，保持一致性
- 审批：查状态 + 更新，异常时整体回滚
- 状态刷新：同一批预约的多次更新要么都生效要么都回滚

注意：**`@Transactional` 默认只对 `RuntimeException` 回滚**，项目里的 `BizException` 继承自 `RuntimeException`，所以能正常回滚。

## 七、定时任务与「懒刷新」

预约状态不能只靠用户操作触发，否则「时段结束后自动完成 / 违约」永远不会发生。

```java
@Scheduled(fixedDelay = 60_000, initialDelay = 15_000)
public void refresh() {
    try {
        bookingService.refreshStatuses();
    } catch (Exception e) {
        log.warn("预约状态刷新失败：{}", e.getMessage());
    }
}
```

三个细节：

1. **`fixedDelay` 而不是 `fixedRate`**：上一次执行完再等 60 秒，避免任务堆积
2. **异常必须吞掉**：定时任务抛异常会导致后续调度停止（取决于线程池配置），这里记录日志继续跑
3. **查询前也刷新一次**：`listByDate` / `mine` / `pageAll` 都会调用 `refreshStatuses()`，保证用户打开页面看到的是最新状态，不用等下一分钟

状态刷新逻辑：

```java
// 已通过且时段已结束
if (checkinAt != null) → COMPLETED
else                   → VIOLATED

// 待审批但时段已开始
→ CANCELLED
```

为什么可以重复执行？因为每次更新都带 `where status = 'APPROVED'` 之类的条件，已经是 `COMPLETED` 的记录不会再次被处理，**天然幂等**。

## 八、统计 SQL 与趋势补零

统计模块的原则：**能在数据库聚合的，不要拉到内存**。

```sql
-- 状态分布
SELECT status AS name, COUNT(*) AS value
FROM booking
GROUP BY status;

-- 设备热度
SELECT d.name AS name, COUNT(*) AS value
FROM booking b JOIN device d ON d.id = b.device_id
GROUP BY d.id, d.name
ORDER BY value DESC
LIMIT 5;
```

趋势查询只返回「有数据的日期」，Service 在 Java 侧补齐缺失日期：

```java
Map<LocalDate, Long> counted = ...;  // SQL 结果
for (int i = days - 1; i >= 0; i--) {
    LocalDate day = today.minusDays(i);
    result.add(Map.of(
        "date", day.toString(),
        "label", day.format(DateTimeFormatter.ofPattern("MM-dd")),
        "value", counted.getOrDefault(day, 0L)
    ));
}
```

为什么要补零？

- 折线图如果缺少日期，X 轴会「跳变」，看起来像数据错误
- 补零后趋势连续，业务上也能看出「某天真的没人预约」

注意 JDBC 返回的可能是 `java.sql.Date`，用 `toLocalDate()` 转换，避免 `ClassCastException`。

## 九、前端：预约矩阵与深色科技风

### 9.1 预约矩阵

数据结构是「设备 × 时段」，用 CSS Grid 渲染：

```html
<div class="matrix" :style="{ gridTemplateColumns: `196px repeat(${slots.length}, minmax(132px, 1fr))` }">
```

为什么用内联 `gridTemplateColumns`？

- 时段数量是接口返回的，CSS 变量在 `repeat()` 里兼容性差
- 内联样式能直接拿到响应式数据，避免动态生成 `<style>`

单元格状态由前端根据「预约记录 + 当前时间 + 设备状态」计算：

| 状态 | 条件 | 样式 |
| --- | --- | --- |
| 可预约 | 无预约、设备可用、时段未开始 | 青色边框，可点击 |
| 待审批 | 有 `PENDING` | 黄色 |
| 已通过 | 有 `APPROVED` | 蓝色 |
| 已完成 | 有 `COMPLETED` | 绿色 |
| 违约 | 有 `VIOLATED` | 红色 |
| 不可用 | 设备维修 / 停用 | 灰色 |
| 已过期 | 时段已开始且无预约 | 暗色，不可点击 |

日期边界：今天起 14 天，`canPrev` / `canNext` 控制按钮禁用，避免用户翻到无意义的日期。

### 9.2 深色主题

- `document.documentElement.classList.add('dark')` 启用 Element Plus 暗色变量
- `styles/global.css` 定义 CSS 变量：背景、面板、边框、霓虹色
- 登录页 / 仪表盘用纯 CSS 做网格背景、光晕、雷达扫描、扫描线
- 所有页面共用玻璃面板：`background: rgba(...)` + `backdrop-filter: blur(...)` + 细边框

### 9.3 ECharts 按需引入

完整 `echarts` 包很大，项目只用到折线、环形饼图、横向柱状图：

```js
import * as echarts from 'echarts/core'
import { BarChart, LineChart, PieChart } from 'echarts/charts'
import { GridComponent, TooltipComponent, LegendComponent, GraphicComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'

echarts.use([...])
```

构建结果：`echarts` chunk 约 531 KB（gzip 179 KB），比完整包小很多。

注意一个坑：`utils/echarts.js` 默认导出的是命名空间对象，页面里要写：

```js
import echarts from '../utils/echarts'
```

而不是 `import * as echarts`，否则会多包一层，`echarts.graphic` 取不到。

### 9.4 侧边栏角标即时刷新

待审批数量在 `MainLayout` 里轮询（60 秒一次），但用户提交预约 / 审批后不应该等一分钟。

方案：自定义事件。

```js
// 提交预约后
window.dispatchEvent(new Event('lab:pending-changed'))

// MainLayout
window.addEventListener('lab:pending-changed', loadBadge)
```

比引入事件总线或 Pinia 全局状态更轻，组件卸载时记得 `removeEventListener`。

### 9.5 构建分包

```js
manualChunks: {
  vue: ['vue', 'vue-router', 'pinia', 'axios'],
  'element-plus': ['element-plus'],
  'element-icons': ['@element-plus/icons-vue'],
  echarts: ['echarts/core', 'echarts/charts', 'echarts/components', 'echarts/renderers'],
}
```

好处：第三方依赖单独缓存，业务代码更新时用户不用重新下载 900 KB 的 Element Plus。
另外只注册项目实际用到的 20 个图标，图标 chunk 从 170 KB 降到 26 KB。

## 十一、面试可能会问

### 基础

1. **为什么用 JWT？和 Session 有什么区别？**
   无状态、易扩展；代价是无法主动失效，需要黑名单或短有效期 + 刷新 token。

2. **JWT 的 payload 能放密码吗？**
   不能，payload 只是 Base64URL 编码，可被解码。

3. **ThreadLocal 为什么要在 `afterCompletion` 清理？**
   Tomcat 线程池复用线程，不清理会导致用户信息串号、内存泄漏。

4. **前端做了权限校验，后端还要做吗？**
   必须。前端可被绕过，后端才是安全边界。

### 并发与事务

5. **唯一索引和先查后插哪个更可靠？**
   并发下先查后插有竞态；唯一索引由数据库保证原子性，捕获重复键异常即可。

6. **`active_key` 为什么取消后要置空？**
   MySQL 唯一索引对 `NULL` 不生效（允许多个 `NULL`），置空即释放占位。

7. **`@Transactional` 什么情况下会失效？**
   同类内部方法调用、非 `public` 方法、异常被吞掉、异常类型不是 `RuntimeException`（默认）、多数据源未配置事务管理器。

8. **审批接口如何防止重复审批？**
   SQL 带 `where status = 'PENDING'`，更新行数为 0 就提示「已被处理」；这是乐观锁思想。

9. **如果两个人同时审批同一条预约会怎样？**
   只有一个 `UPDATE` 能命中 `PENDING`，另一个返回 0 行并提示刷新，不会产生两次审批记录。

### 状态机与定时任务

10. **为什么需要定时任务？**
    状态变化不只由用户触发：时段结束要自动完成 / 违约，超时未审批要自动取消。

11. **`fixedDelay` 和 `fixedRate` 的区别？**
    `fixedDelay` 是上一次执行完再等，`fixedRate` 是固定频率；任务耗时可能超过间隔时，`fixedRate` 会堆积。

12. **定时任务如何保证幂等？**
    每次更新都带状态条件，已流转的记录不会被再次处理。

13. **签到窗口为什么设在开始前 30 分钟？**
    既要允许学生提前到场，又要防止提前太久「占坑不签」。

### 统计与前端

14. **为什么统计用 SQL 聚合而不是 Java 循环？**
    数据量大时内存和网络开销高；数据库有索引和聚合优化。

15. **趋势图为什么要补零？**
    保证 X 轴连续，避免折线跳变和误判。

16. **ECharts 在 Vue 里要注意什么？**
    容器有宽高、初始化一次、监听 resize、卸载时 `dispose`。

17. **为什么用 `manualChunks` 分包？**
    第三方依赖体积大且不常变，单独分包可利用浏览器缓存，业务代码更新不影响依赖缓存。

18. **自定义事件和 Pinia 怎么选？**
    简单的一次性通知用事件更轻；跨页面共享状态用 Pinia。

## 十二、动手练习（建议按顺序）

1. **加「预约详情」抽屉**：点击矩阵中的预约格，展示申请人、用途、审批人、签到时间。
2. **加「设备可用率排行」**：统计每台设备近 30 天的被预约时长，柱状图展示。
3. **把签到改成扫码**：生成带预约 id 的二维码，扫码后调用签到接口（先不做真实扫码，用输入框模拟）。
4. **加「违约次数」限制**：用户违约 3 次后禁止预约 7 天，写一个 Service 校验 + 单元测试。
5. **给审批加备注模板**：常用驳回原因（设备检修 / 时段冲突 / 信息不全）一键填充。
6. **加导出功能**：把「我的预约」导出为 CSV，后端用 `StreamingResponseBody`。
7. **写 3 个单元测试**：创建预约成功、重复时段失败、审批自己的预约失败。
8. **做一次压力测试**：用 JMeter 或 `curl` 并发 20 个相同预约请求，验证只有 1 条成功。

做完前 5 个，第二阶段就算真正掌握了。

## 十三、下一阶段预告

第三阶段会围绕「实时性」和「性能」展开：

- **Redis 缓存**：设备列表、分类列表、统计数据，设置合理过期时间
- **分布式锁**：抢约场景下用 `SETNX` 做前置削峰，数据库唯一索引仍然保留
- **WebSocket**：审批结果实时推送给申请人，看板占用状态自动刷新
- **消息通知**：预约成功、审批通过 / 驳回、签到提醒
- **工程化**：Docker Compose 一键启动、GitHub Actions 自动构建、Swagger 接口文档

到那时你会真正体会到：**缓存是性能优化，不是正确性保障；正确性最终还是要靠数据库约束和状态机。**
